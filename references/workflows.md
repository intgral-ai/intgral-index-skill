# 按工作场景查找与协作

只读取与当前请求有关的分支。

## 成员开始使用或恢复工作

定位当前目标、角色映射、平台入口和已在推进的任务。配置存在时按需读取；缺少配置时先提供可执行的角色级指导，只询问阻碍下一步的关键资料。工作目录和私有配置由成员选择，保持模型客户端和个人机器路径独立。

完成标准：成员知道本次要推进的结果、适用来源和第一步动作。

## 新需求、客户反馈或跨团队事项

1. 分清原始问题、已知证据、成员建议和已经作出的承诺。
2. 找到有关项目或任务并查重。说明对当前目标的作用与依赖。
3. 给出推进角色、需要的输入、待决定事项和最小交付。只有缺口影响决定时才补研究或设计。
4. 请求要求落地时，按授权创建或更新正式任务，并关联原讨论和资料。对外承诺或发送仍须来自本次请求的授权。

完成标准：下一位参与者能直接行动；未知项有明确的核实动作。

## 项目或阶段规划

先明确阶段结果和可观察的成功证据，再核对现有项目、可用资源、依赖和未完成承诺。将候选工作区分为建议和已确认承诺。需要正式计划时，每项工作明确推进负责人、交付和验收；任务大小、周期和同时进行数量沿用团队的当前约定，避免复用已过期的数字限制。

完成标准：本阶段要达成什么、取舍是什么、负责人和阻塞可追溯。

## 设计、研发与交接

根据任务查找 Figma 中的设计系统及选定版本，或 GitHub 中的目标仓库、分支和实现。UI/UX 实施和评审对齐 Figma，代码事实对齐实际提交。缺少设计依据、技术决定或输入时，将其列为具体缺口。

交接通常只需：结果或产物链接、验证依据、待核验事项、下一步及参与角色。保留每个来源的适用版本。模型完成、测试通过、实现合并、人工接受和客户目标达成分别记录。

完成标准：接手的人能找到原始产物、复现必要验证并知道下一步。

## 研究探索与会后推演

会议结束后的 Codex 讨论、研究与实验仍是工作来源。在本次请求或已确认团队配置授权持续记录时，出现有依据的新发现、重要未知、排除方案、实验结果或明确选择，及时提炼到主题记录；不必等会议或日报。“记一下”触发保存，“先验证”记录验证计划，“确认采用”须核对确认者及范围。仅请求讨论建议、没有同步授权时，先给可保存的草稿；skill 和外部来源本身不授予写入或发送权限。

读取 `collaboration_policy.knowledge_capture` 及其记录规则，确定 docs 研究入口、待同步目录、目的频道与既有授权。各成员的 Codex 使用自己的账号向共同入口写入；一台电脑上的每日自动化只能补办可访问的记录，不能宣称覆盖其他成员的本地聊天。

### 留痕和确认

按主题先查已有文档，研究记录放在配置指定的 Research 入口；日报和原会议链接该主题，不按每段对话复制一份。通常只需：**发现或问题、依据及来源、当前判断、未知或反证、下一步验证**，附状态、事件时间和来源定位。原始聊天只作为依据，不整段搬运；没有可访问的对话链接时说明来源范围，不虚构链接或自动创建公开分享。

| 状态 | 含义 |
|---|---|
| 探索中 / `exploring` | 有价值的发现、方向或假设，尚未决定采用 |
| 待验证 / `validating` | 验证方法与观察信号已说明，结果仍未知 |
| 已决定 / `decided` | 有权负责人已明确确认，并记录确认人、时间、依据和适用范围 |

“有意思”“不错”、AI 推荐和沉默均不代表采用。“先试 A”可以确认一次限定范围的实验，不能扩写为全面采用 A。缺少确认依据时保持探索或待验证，记录待确认事项；被替代的判断和决定保留更正及关联历史。决定的取舍、影响和复核条件按下方决策流程补齐。

### 写入和待同步记录

为每条记录分配稳定 `record_id`，内容变化递增 `revision`，保留 `occurred_at`、`updated_at`、主题、状态、提炼正文、原始证据及 `confirmation`（没有确认则为 `null`）。docs 正文保留记录 ID 和修订号以供查重；修订更新同一主题原条目，不覆盖成员补充。

配置了私有 `outbox_path` 时，每条记录保存为一个 JSON 文件，先落盘再尝试远端写入；路径从工作区根目录解析，目录不进入共享 Git。分别维护 `delivery.docs` 和 `delivery.slack` 的状态、目标链接、已验证修订号及必要消息时间戳，状态使用 `pending`、`verified` 或 `not_requested`。未确认内容不能通过重试升级为决定。没有本地文件能力时直接按授权写 docs；无法写入时交付草稿，明确它尚未进入自动补办队列。

docs 写入并重新加载复读后，才确认该修订已保存。Slack 仅在当前请求或计划已授权时向配置频道同步；通常由每日总结汇总，立即回告须在配置或请求范围内，发送前检查已有回告。发送状态不明先查频道，不盲目重发；docs 已成功而 Slack 失败时只补发送。失败时保存记录和错误阶段，不能把“尝试”说成“已同步”。

### 每日补齐与团队可见性

每日总结读取新增或修订的主题记录、可访问的待同步队列，以及团队更新线程中的成员反馈。先补 docs，再把重要探索、待验证事项和已确认决定分别列入当日摘要，附主题原文链接；沿用一天一个主帖及实质更正回复的规则。记录 ID、修订号和来源事件共同去重，自动摘要和回声不算新证据。已即时回告的记录不原样重发；后续只发送实质变化或在日报中链接已有回告。

docs 与 Slack 的完成状态分别核实；单项失败不阻断其他已验证交付。每日总结只整理和同步，不替负责人作出决定，不因一句探索自动建立正式任务。没有新记录时保持安静，不创建重复计划。

完成标准：有价值的发现可找回，记录状态与确认依据一致，docs 原文和频道增量可追溯，未同步的修订仍可续办。

## 会议、日志与决策

### 从来源到记录

先查私有配置中的工作流、会议归档规则、决策文档和 `collaboration_policy`，只加载本次主题相关的更新。通常沿 Slack 讨论与口头分工、Linear 正式任务、GitHub 提交/PR/检查、Figma 设计、客户与业务证据、会议原文互相核对。记录来源链接、事件时间、适用版本和已覆盖范围。会议转录或可靠原文用于核实自动总结；未确认的说话人、负责人、期限和承诺保留未知。

会议来源以私有配置中已启用且可访问的来源为准；已停用来源不连接、不重试。可用来源包括会议笔记、录屏、转录和摘要。先核对授权账号与实际可读取范围，连接待确认时保持待接通。分别标记录屏、逐字转录和 AI 摘要的可用性；只有录屏链接不能声称已读转录。处理中的转录稍后重试。跨平台按会议发生时间、主题、参与者和来源标识核实同场关系，确认后合并到原会议页并保留双来源；重复系列的会议 ID 不能单独用作每场的去重键，优先使用 occurrence UUID 与实际开始时间。录屏保留受权限保护的来源链接，不扩大可见范围。

会议在 docs.intgral.ai 按“Meeting → YYYY-MM-DD → 主题”归档，标题接主题；日期按团队当前时区规则。会议保留简短摘要、讨论要点、明确决定、原文明示行动和未决问题，空栏目省略。日期下维护中央工作日志，每个相关会议维护“当天执行日志 · YYYY-MM-DD”，两者互链并引用原始事件。只在有相关变化时补历史会议的执行日志，保留人工内容与已有链接。

每日 logs 顶部维护最新有效摘要，逐项附证据与适用截止时间；后续确认替代旧结论时更新该摘要并链接替代依据。历史快照和更正保留在下方，明确适用窗口，避免旧快照被当成当前结论。用简洁 bulletpoints 写实际进展、决定、分工、阻塞和下一步。区分口头 assignment 与 Linear 正式分配；区分 PR 打开、评审、合并、测试、部署、验收和业务结果。说明实际截止时间、覆盖缺口和跨日归属；“未查到记录”不能推断“没有进展”。相同事件跨来源去重，新证据修订原条目并保留更正依据。扫描频率、时区、通知和重试规则从已获授权的自动化读取；记录规则本身不授权创建、修改定时任务或向其他渠道发消息。

### 从记录到决定

准备决定时，围绕一个明确问题串联：当前目标 → 相关既有决定 → 此前 updates 与会议总结 → 最新任务、交付和客户证据 → 候选方案。历史 updates 指当前工作线的先前记录，不因此越过归档边界读取旧项目。必要时沿摘要回读原文，避免摘要互相引用却没有直接依据。

- **事实与差异**：发生了什么、证据支持到哪里、与上次讨论相比变了什么；观点、假设、提议与已确认决定分别标记。
- **选项与取舍**：推荐方案、可行替代、成本/依赖/风险、尚缺证据，以及补证据的具体动作。资料冲突时并列来源、日期和版本，不以“最新消息”自动取代正式决定。
- **确认与记录**：由当前项目或职责记录中的有权负责人作出决定；AI 的推荐、沉默、出席或会议自动总结不代表批准。证据不足可记录暂缓或待验证。

决定记录至少能回答：决定了什么、谁在何时确认、依据哪些 updates/会议/原始证据、为何取舍、适用范围、影响哪些计划与任务、何时因何种新证据重新评估。替代旧决定时链接被替代记录并保留历史；只有负责人明确确认后才改为已决定。

### 从决定回到执行

长期决定进入主题文档或决策记录，计划同步引用决定。工程统筹按依赖拆分交付，商务职能把客户与增长工作接入；实际角色从私有配置解析，不把职能导航变成额外管理层。正式任务在 Linear 维护推进负责人、交付、验收与依赖，设计依据连接 Figma，代码与验证连接 GitHub。

成员和 AI 在授权范围内小步执行、直接协调，结果与阻塞进入后续 updates、相关会议日志和复盘。日志不覆盖任务系统状态；合并不自动代表发布、验收或业务目标达成。新证据触发复核而不静默改写原决定。

完成标准：成员能从决定追溯输入依据，从决定找到负责人和执行任务，再从结果回到下一次讨论；未知项与待确认事项仍可见。

## Pivot、归档或环境清理

只有成员明确要求改变目录、归档旧资料或清理资源时进入此分支。先确认范围、真实路径、资源归属、Git 与未提交状态、worktree 关系和当前进程。给出当前与历史资料边界，保留迁移映射及必要的兼容入口。

需要删除资源时，先备份要保留的数据并验证备份，按明确归属逐项处理。归属不明或缺少必要授权的部分保留，继续完成独立可做的工作。执行后核对 Git 状态、路径与链接、备份和资源清单。更新私有 context，明确哪些旧决定已被新决定替代。

完成标准：当前入口可用、历史数据可追溯、已保留内容可恢复、未处理项与限制明确。一次获准的迁移不授权以后自动重复清理。
