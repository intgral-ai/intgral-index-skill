# 从愿景到工程的更新

用户明确要求更新产品/MVP/engineering 时才读取此文件。先定位并完整读取现有主文档、相关会议全文和当前确认记录，保留原 URL 与有用评论。

## 建立变更依据

为这次变更列出：议题、原有有效决定、新证据、确认人/时间、拟修改位置、影响及状态。明确用户在当前会话给出的确认同样有效，不重复询问已回答的问题。来源发生冲突时核对确认权、范围和时间；无法解决的冲突列待确认，不能简单采用最新一次 AI 总结。

“讨论过”“可以试试”“某人也许能做”、summary 的 next steps 与个人 thoughts 不构成产品承诺。没有证据建立负责人、预算、日期、发布策略和验收阈值时保留待确认。必要时提出少量会改变方案的问题，同时继续独立可做的写稿与核对。

## 按依赖顺序写回

| 层级 | 要更新的内容 | 向下游提供的约束 |
|---|---|---|
| 产品愿景 | 服务谁、解决什么问题、交付价值、长期方向、本阶段验证假设 | 已确认方向、当前边界、尚未选择的领域/能力 |
| MVP | 对应假设的用户闭环、首版包含/不含范围、发布方式、验证样例、验收与成功信号 | 可执行场景、明确排除项、待定门槛和依赖 |
| Engineering | 每个场景所需能力、数据与状态、接口、失败处理、验证方式、交付顺序 | 已确认 owner/排期，以及逐项待确认的架构、runtime、成本或分工 |

工程项必须能追溯到 MVP 场景；不要把探索中的技术选择写成已落定架构。MVP 的长期愿景引用到路线图，不挤入首版承诺。旧文档里与新确认冲突的内容标为被替代并关联依据，仍适用的内容保留。

文档开头给出当前版本、适用范围与来源覆盖。重要待确认项放在对应段落，同时收敛到短表：`问题 / 当前假设 / 所需证据或确认角色 / 对首版影响`。角色未知就写待确认，不为填表指派具体人。

写后横向复核三份文档中的交付物、发布方式、日期、成本与术语是否一致；逐份 reload 验证。只将本次实际验证过的结果写进会议/当天日志。正式 Linear 任务、看板状态和团队消息沿用既有 work_tracking / communication 授权与证据门槛，不由文档草稿自动产生。
